# Limitations

Vina-Ion-Metal 1.0.0 is a research tool. The following limitations are known
and should be considered before production use or publication.

1. **Metal weights are heuristic, not calibrated.** The defaults
   (vdw 1.2, cn 0.5, geom 1.0) are literature-informed provisional values;
   a multi-protein calibration benchmark (≥10 metalloprotein complexes with
   crystallized coordinating ligands, regression over the weight triplet) is
   still pending. A runtime notice reminds the user whenever coordination
   scoring is active. Treat the tool as a mechanistic pose filter, not an
   affinity predictor.

2. **Cu²⁺ and Ni²⁺ parameters are estimates.** AutoDock 4 never calibrated
   these ions. Their AD4-style parameters are placeholders; the ions are now
   *reachable* through `scripts/prepare_receptor.py` (audit #5 fixed), but the
   underlying values must be validated or supplied through `--metal_params`
   before drawing conclusions.

3. **Fe²⁺/Fe³⁺ share generic AD4 iron parameters.** PDBQT does not encode
   oxidation state; declare it with `--metal_oxidation Fe=3`. Both entries
   currently use the AD4 generic iron values; oxidation-state-specific
   refinement (Harding 2006 distances per state) is pending.

4. **Rigid receptor.** The metal and its rigid coordinating residues do not
   reorganize. Flexible side chains (`--flex`) are treated as movable donors
   inside the coordination shell (they compete with the ligand for the CN
   target), but their typing must be correct.

5. **Receptor occupancy is a typed donor count.** The CN target is reduced by
   the number of rigid receptor atoms typed as coordination donors (N/O/S XS
   types) inside the ion's cutoff — a hard integer. A typing-independent
   geometric count is now reported as a diagnostic when the two disagree
   (audit #10), and `scripts/prepare_receptor.py` prints the same information
   before docking; an occupancy of 0 with N/O/S atoms nearby should be
   investigated, not ignored.

6. **Pregenerated maps.** `--maps` assumes maps generated by Vina-Ion-Metal,
   where parametrized metal ions are excluded from donor-type maps. Mixing
   maps from unmodified Vina with Vina-Ion-Metal scoring would double-count
   some interactions.

7. **Hydrogens are excluded from coordination typing.** The full directional
   AD4Zn model (nbp_r_eps, TZ/ZA pseudoatoms, Zn–H interaction) has not been
   ported; donors are typed by heavy atom (N/O/S). The stale
   `data/AD4Zn.dat` of VinaMetal 1.0.0 was removed (it was a mislabeled copy
   of `AD4.1_bound.dat`); if porting the directional model, take the
   parameters from the upstream AutoDock repository.

8. **Ligands bridging two metals.** Each ion evaluates its own shell, so the
   energy is supported, but shared sites are penalized independently by each
   metal's CN term. Validate bridging geometries manually.

9. **Stouten desolvation is ported but inactive.** The ionic `vol`/`solpar`
   fields are available, but the metal-specific desolvation term is deferred
   to the post-calibration phase to avoid double counting with Vina's implicit
   desolvation.

10. **Preliminary validation.** The regression suite (byte-identical scoring
    against stock Vina 1.2.7 without parametrized metals; gradient checks;
    CN detection) is CI-enforced, but the metalloprotein validation set is
    still the two re-docking systems inherited from VinaMetal (GlfT2 / PDB
    4FIY, Mn²⁺; PDB 1s63, Zn²⁺). Numbers shift with respect to VinaMetal
    1.0.0 because of the lenient CN default (audit #2) and the heuristic
    weights (audit #9); re-run the bundled examples to reproduce them. A
    larger multi-complex benchmark and leave-one-out calibration remain
    pending.

11. **Linux x86-64 release only.** The GitHub Actions workflow produces
    prebuilt assets only for Linux x86-64 (this is an intentional scope
    decision for v1.0). Windows/macOS users can build from source; see
    `docs/INSTALL.md`.
